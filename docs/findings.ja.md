# 実測メモと設計判断

TapMute を作る過程で、設計書の前提が実機と食い違った点と、その結果どう作り直したかの記録。
「どう動くか」は README に、「なぜそう作ったか」はここに置いてある。

計測環境: macOS 26.5 / Apple Silicon / Swift 6.3、2026-08-30。

---

## 1. メディアキーは CGEventTap では抑制できない

**前提としていたこと。** `CGEventTap` で `systemDefined` を捕まえ、会議中だけ消費すれば、
ミュートしつつ音楽が再生されるのを防げる。参考にした Hammerspoon 版もこの方式だった。

**起きたこと。** ミュートは効くのに Music が起動してしまう。

**測ったこと。** 消費するだけのタップを 2 つのタップ位置で用意し、実際にボタンを押して確かめた。

| タップ位置 | PLAY の捕捉 | 消費した結果 |
|---|---|---|
| `cgSessionEventTap` | できる | **Music が起動する** |
| `cghidEventTap` | できる | **Music が起動する** |

合成イベント（`NSEvent.otherEvent` を `.cghidEventTap` へ post）では Music が反応しなかったため、
自動テストでは切り分けられず、実キーでの判定が必要だった。

**結論。** now playing の配送（`mediaremoted`）は CG イベントパイプラインの外にいる。
どこで消してもメディアキーは届く。

**対処。** 会議中だけ Now Playing の座を奪う。`MPRemoteCommandCenter` にコマンドを登録し、
無音ループを再生して「いま再生しているアプリ」になると、OS はメディアキーを Music ではなく
こちらへ配送する。**会議中だけ**というのが肝で、常時奪うと音楽の操作ができなくなる。

イベントタップは「押された瞬間を知る」用途で残した。Now Playing 側のコマンドハンドラは
通常は握り潰すだけの盾で、入力監視が切れてタップが動いていないときだけ自分でミュートする。

## 2. `kAXWindowsAttribute` は現在の Space のウィンドウしか返さない

**前提としていたこと。** ウィンドウ題名は AX で取れる。`CGWindowListCopyWindowInfo` は
題名取得に画面収録権限が要るので避ければ、ユーザーに求める権限を 1 つ減らせる。

**起きたこと。** Zoom も Dia も起動しているのに AX 上はウィンドウ 0 件。

**測ったこと。** 別 Space に置いたアプリで各経路を比較した。

| 経路 | 別 Space のウィンドウ | AX 要素 | 権限 |
|---|---|---|---|
| `kAXWindows` | **取れない** | あり | アクセシビリティ |
| `kAXMainWindow` / `kAXFocusedWindow` | 取れる | あり | アクセシビリティ |
| `CGWindowList` | 取れる | なし | 画面収録 |

**結論。** 会議を別デスクトップに置いて手前で作業するのは普通の使い方なので、
AX 単独の検出は実運用で沈黙する。設計書の「権限を 1 つ減らす」判断は、
この挙動を知らずに立てられたもの。

**対処。** 3 経路を束ねて 1 つのウィンドウ一覧にする。同じ題名が複数経路から来たときは
AX 要素を持つものを優先して残す（前面化とタブ操作に要素が要るため）。
画面収録は「推奨」として案内し、無い場合も上 2 経路で動くようにした。

## 3. Chromium 系はページ内容の AX ツリーを作らない

**起きたこと。** Meet の検出とミュートは動くのに、ミュート状態だけ読めない。

**測ったこと。** ブラウザのウィンドウを走査してもノードが 111 個しか無く、
ページ本体に到達していなかった。アプリ要素に `AXManualAccessibility` を立てると
3581 ノードまで展開され、`[AXButton] "Turn off microphone"` が depth 15 で見つかった。

**結論。** Chromium はスクリーンリーダーの存在を検知するまでページの AX を作らない。
加えて、探索の深さ上限を 14 にしていたため、仮にツリーがあっても届いていなかった。

**対処。** ブラウザを見るプロファイルのときだけ `AXManualAccessibility` を立て、
深さ上限を 30 に上げた。会議を検出している間だけ立てるので常時のコストにはしない。

## 4. ミュート状態の文言は「状態」と「操作」で語幹を共有する

**起きたこと。** Zoom では正しく読めた判定が、Teams では常に「解除中」に張り付いた。

**測ったこと。** Teams の実際のボタン文言と TapMute の表示を 1 秒ごとに 30 回並べて記録した。
Teams 側は「マイクのミュート」⇄「マイクの**ミュートを解除**」と切り替わっているのに、
表示は終始「ミュート解除中」だった。

**結論。** 2 つの罠が重なっていた。

1. **助詞。** Zoom は「ミュート**解除**する」と繋がるが、Teams は「ミュート**を**解除」と
   助詞が入る。部分一致では前者の語で後者を拾えない。
2. **状態語と操作語の衝突。** `ミュート解除` は Zoom では操作（＝いまミュート中）だが、
   Zoom のタブグループ説明では「ミュート解除**された**」＝状態（＝いま解除中）を指す。
   Teams の動画タイルでも状態として現れる。1 つのリストに混ぜると必ずどちらかで誤判定する。

**対処。** 判定の軸を「操作ボタンの文言」優先に変えた。**ボタンは常に次にする操作を述べる**ので、
「解除」を提案していれば今はミュート中だと確実に分かる。状態を述べる語は別リストにして、
ボタンが見つからないときの保険に降格させた。

| アプリ | ミュート中 | 解除中 | 深さ |
|---|---|---|---|
| Zoom | 自分のオーディオをミュート解除する | 自分のオーディオをミュートする | 浅い |
| Teams | マイクのミュートを解除 | マイクのミュート | 20 前後 |
| Meet | Turn on microphone | Turn off microphone | 15 前後 |

実機で採取したこの文言に対する回帰チェックを `--probe-mute-markers` として残した（11 件）。
判定が狂ったとき、AX を掘り直す前にここで切り分けられる。

## 5. CoreAudio の入力稼働フラグはミュート状態に使えない

ミュート状態を軽く取る方法として `kAudioDevicePropertyDeviceIsRunningSomewhere` を検討したが、
**Zoom はミュート中も入力ストリームを掴んだまま**で、常に「使用中」に見えた。

通話中かどうかの目安にはなるので、誤検出対策の任意設定
（「マイク使用中のときだけ会議とみなす」）としてだけ採用した。既定は無効。
これを必須にすると、もしミュート時にストリームを手放すアプリがあった場合、
**ミュート解除ができなくなる**（＝より悪い失敗）ため。

## 6. TCC はコード署名の designated requirement で紐づく

**起きたこと。** 1 行直して入れ直すたびに、権限を付け直す羽目になっていた。

**測ったこと。** 署名方式ごとに要件を出力して比較した。

```
アドホック        designated => cdhash H"114f5471..."
Developer ID      designated => identifier "io.github.genkitoyama.tapmute"
                                and anchor apple generic
                                and certificate leaf[subject.OU] = <TeamID>
```

**結論。** アドホック署名はバイナリのハッシュで紐づくので、コードが変われば別アプリ扱いになる。
安定した署名 ID なら バンドル ID + チーム ID で紐づくため、再ビルドしても維持される。

**対処。** Makefile が `security find-identity` から署名 ID を自動検出するようにした。
証明書が無い環境ではアドホックに落ちる。バンドル ID か署名方式を変えた直後だけは
`tccutil reset` してから付け直す必要がある。

## 7. Dia のタブは `AXUnknown` だが `AXPress` が効く

Chrome 系は `AXTabGroup > AXRadioButton` でタブを公開するが、Dia のタブは `AXUnknown` で、
ロールからは判別できなかった。ただし `AXPress` アクションは持っている。

そこでタブの探索は**ロールではなく「押せること」と「題名が一致すること」**で行うようにした。
これで Chrome と Dia を同じコードで扱える。非アクティブタブの Meet も、
タブを一瞬切り替えてミュートし、元のタブへ戻せる。

## 8. Slack ハドルは題名に何も出ない

**起きたこと。** Slack をプロファイルに足そうとしたが、題名で判定できなかった。

**測ったこと。** ハドル前後でウィンドウ題名を比べた。どちらも
`<会話名> - <ワークスペース> - Slack` のままで、ハドル中かどうかの手がかりが無い。
一方、AX ツリーにはハドル中だけ現れる要素があった。

```
[AXToolbar] desc="Huddles actions"
[AXButton]  desc="Leave Huddle"
[AXButton]  desc="Mute microphone"   ← actions=["AXPress", ...]
```

**結論。** 題名ベースの検出はこのアプリには使えない。要素の有無で判定するしかない。
なお `huddle` を単純に含む語で探すのは危険で、`Start huddle in <channel>` ボタンは
ハドルしていなくても常に存在する。`Leave Huddle` のように**ハドル中だけ現れる語**を選ぶ必要がある。

**対処。** 検出方法をプロファイルの属性にした（`.windowTitle` / `.axElement`）。
要素走査は題名比較よりずっと重いので、**マイクが使用中のときだけ**動かす。
ただし既に検出済みのアプリは対象から外さない。ミュート中に入力デバイスを手放すアプリがあった場合、
マイク条件だけだとミュート解除ができなくなるため（5 章と同じ理由）。

**副産物。** ミュートボタンが `AXPress` を持っていたので、Slack はキー送出ではなく
ボタンを直接押す方式にした。前面化が要らないので、Meet や Teams で避けられない
Space の切り替わりが起きない。操作方法もプロファイルの属性にしてある
（`.globalShortcut` / `.focusThenShortcut` / `.pressControl`）。

**バックグラウンドで押せるかの検証。** ハドル中でなくても確かめられる。Slack を背面に置いたまま
可逆なトグル（フォーカスモード）に `AXPress` を送り、ボタン自身の説明が反転するかを見た。

```
Slack は前面か: false
押す前:   "Turn on focus mode"
押した後: "Exit focus mode"      ← 効いている
復帰後:   "Turn on focus mode"
```

前面化せずに押せることが確認できた。Electron アプリ全般に同じ手が使えるはず。

なお、自分宛て DM にはハドルボタン自体が存在しない（実測）。一人で試すならチャンネルで
`Start huddle in <channel>` から開始する必要がある。

## 設計判断

**検出はキャッシュ、タップは読むだけ。** AX 走査は数十 ms かかることがあり、
イベントタップのコールバックが遅いと OS にタップを無効化される。
3 秒タイマーとワークスペース通知でバックグラウンドに走らせ、
キー押下時はキャッシュを読むだけにした。無効化された場合の再有効化も入れてある。

**読めないものは表示しない。** ミュート状態が読めなかったときは、状態表示をやめて
「状態不明」とメニューに出す。確実に読めないものを状態として出すと、必ず嘘をつく瞬間ができる。

**アプリごとの差は値に落とす。** 検出方法・ショートカット・前面化の要否・状態判定の文言を
`MeetingProfile` の値として持たせた。Teams の追加が実質データ追加だけで済んだのはこの構造のため。

**自動切り替えは「直前に無かったデバイス」だけ。** デバイス一覧の変化すべてに反応すると、
ユーザーが手で選び直した設定と喧嘩する。

## 名前を変えた理由

当初の `MeetMute` は「Meet」が Google Meet を指すように読め、Zoom / Teams も対象なのに
機能の 3 分の 1 しか表していなかった。また、何をどうするアプリなのかが名前から落ちていた。

`TapMute` は「押すとミュート」という操作と結果を含み、特定の会議サービスに寄らない。
既存の Mute 系アプリ（Mic Drop / Mutify / MuteDeck / MuteMe / MutePod）とも衝突しない。

## 調査に使ったコマンド

```sh
make probe-windows                    # 検出結果と全ウィンドウ題名（3 経路のどれで見つけたかも出る）
make probe-keys                       # メディアキーが届いているか（消費しない）
./build/probe --probe-mute-markers    # ミュート判定の文言テスト
./build/probe --probe-audio           # オーディオデバイスと自動切り替えの対象
```

いずれもターミナル自身の権限で動くので、アプリに権限を与える前の切り分けに使える。
